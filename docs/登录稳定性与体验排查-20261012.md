# 登录稳定性与体验排查（2026-10-12）

本报告记录修复前的原因排查与优化评估；当时仅只读取证。用户反馈为：正常退出工作台，次日重开后，平台官网也可能要求重新扫码。用户随后授权修复，实施结果见 [1.0.6-rc.11 版本说明](releases/v1.0.6-rc.11.md)，下文代码位置和日志均为排查时的快照。

## 结论

目前证据不支持把两个平台的问题统一归为“退出时没保存 Cookie”。真实安装版记录显示 Cookie 恢复、写盘成功；视频号的关键 Cookie 仍在磁盘且未到本地有效期，但平台身份响应曾被识别为登录失效，随后页面持续回到登录页。快手同时存在主页与创作者后台票据不同步、保活任务无法开展主页复核，以及主页短暂访客界面被立即判离线的问题。

这些问题需要分别处理。平台拒绝已有会话的具体触发条件，现有日志不足以区分服务端时限、会话轮换或其他设备/会话校验；不能据此宣称所有隔夜失效都已经找到唯一根因，也不能保证修改本地 Cookie 有效期就能解决。

## 登录与连接问题

### 1. 快手保活会被自己阻止

调度器先把保活任务标为 `running`，再调用 `accounts.checkStatus()`；主页复核检查发现该账号存在运行中的任务就返回 false，没有排除保活自身。无主页实例、或页面停留在管理后台时，这条路径会保留旧结论，保活被跳过。

依据：[scheduler.ts](../src/main/data/scheduler.ts#L369)、[scheduler.ts](../src/main/data/scheduler.ts#L430)、[account-service.ts](../src/main/services/account-service.ts#L481)。实际最近 7 次跳过与这条路径一致，但历史日志不足以证明每次都由同一个条件造成。

已用真实 CollectScheduler、AccountService 与内存 SQLite 组合复现：保活任务结束时为 skipped，主页导航与检测次数均为 0；同一账号在保活任务结束后直接检查，主页导航与检测次数均为 1，获得新确认。复现的跳过原因与实际日志一致。产物：`output/keepalive-self-block-reproducer.mjs`、`output/keepalive-self-block-reproducer.results.json`。

建议让任务协调明确区分登录检查与数据采集，允许保活执行自己的只读主页复核，同时继续保护其他采集、消息和编辑任务。验收必须覆盖“无页面 + 保活正在运行”的组合。此修复改善运行中的检查，不能让已经退出的程序继续保活。

### 2. 快手主页的瞬时访客界面可直接覆盖在线状态

主页出现明确登录按钮后，识别脚本立即返回 offline。等待 SPA 加载的循环对 offline 也立即返回，而后续负面双确认分支明确排除了 `source === homepage`。慢加载时可能发生：先显示访客按钮 → 工作台写入离线并提醒 → 页面随后恢复当前账号控件。

依据：[homepage-login.ts](../src/main/browser/homepage-login.ts#L302)、[account-service.ts](../src/main/services/account-service.ts#L746)、[account-service.ts](../src/main/services/account-service.ts#L607)。

已用真实 AccountService 与主页检测脚本、合成网页和内存数据库复现：第一次只检查一次就持久化 offline、产生一次掉线提醒并释放临时页；随后 DOM 为 online，数据库仍为 offline。复现产物：`output/login-hydration-reproducer.mjs`、`output/login-hydration-reproducer.results.json`。它证明代码存在误报路径，不证明用户所有重新扫码都由该问题导致。

建议主页负面结论也做稳定性复核，导航或 Cookie 变化时丢弃旧观察，并在复核完成前保留临时检查页。

### 3. 主页登录与创作者后台登录被压成一个账号状态

快手入口分别为 `www.kuaishou.com` 和 `cp.kuaishou.com/profile`。当前账号状态以主页为准，保活本质上主要做身份检查，不能证明后台票据已经续期。

依据：[platforms.ts](../src/shared/platforms.ts#L167)、[login-detector.ts](../src/main/browser/login-detector.ts#L222)、[scheduler.ts](../src/main/data/scheduler.ts#L430)。

建议界面分别显示“主页可用 / 管理后台待登录”，需要管理功能时在同一账号分区内打开官方入口，让平台完成正常会话恢复，并记录恢复是否成功。不要把本地延长 Cookie 保存时间显示成服务端续期。

### 4. 视频号应补足重启前后的失效证据

现有视频号记录能排除已观察到的关键 Cookie 未落盘这一简单解释，却不能解释平台为何拒绝这份会话。身份解析将多个平台错误码折叠为同一个理由，审计未保存精确错误码；Cookie 变更回调也未记录删除/到期原因。

依据：[identity-evidence.ts](../src/main/browser/identity-evidence.ts#L197)、[identity-observer.ts](../src/main/browser/identity-observer.ts#L146)、[cookie-guard.ts](../src/main/browser/cookie-guard.ts#L83)、[account-service.ts](../src/main/services/account-service.ts#L653)。

建议加入不含凭据的诊断链：保存结果、启动恢复结果、Cookie 名称/域/本地到期时间、变更原因、身份接口状态码及平台错误码、是否跳到登录页。随后对新鲜登录做“立即正常退出重开”和“隔夜正常退出重开”对照，再与普通浏览器各自独立的登录会话比较。立即重开就失效更应检查重启恢复；只有隔夜失效则需要进一步核对平台的会话期限与校验。不能使用代码中的 `sessionTtlHours:48` 当作官方承诺，当前相关流程也不会因为这个常量而强制退出。

### 5. 网络恢复会丢失原页面上下文

网络撤销会销毁网页但保留账号分区。前台恢复时重建页面可能默认加载 `routes.home`，把原快手主页带到创作者后台，增加再次登录的观感；它属于网络/休眠恢复问题，与用户本次正常退出流程分开看。

依据：[ViewHost.tsx](../src/renderer/features/browser/ViewHost.tsx#L63)、[view-pool.ts](../src/main/browser/view-pool.ts#L320)、[view-pool.ts](../src/main/browser/view-pool.ts#L459)。

建议保存用户最后明确选择的页面上下文，重建时恢复只读页面。增加“重建连接”操作，保留登录数据，让用户不必用“重置登录环境”来处理连接故障。

## 体验优化顺序

| 优先级 | 当前问题 | 建议与可见收益 |
|---|---|---|
| 第一批 | 登录、连接和本次检查结果混在一起；新原因只在悬浮提示 | 同时展示登录状态、连接状态、最近确认时间；给出对应的复核或扫码按钮。依据 `AccountLoginStatus.tsx:16` |
| 第一批 | 发布页未保存为计划的文案只放在内存 Map | 按账号自动保存本地草稿，显示保存时间，重启恢复。依据 `PublishPage.tsx:30,98` |
| 第一批 | 从总览点平台，可能继续显示之前另一平台的账号详情 | 统一导航动作，打开平台时清除旧账号详情选择。依据 `OverviewPage.tsx:249`、`MetricsPage.tsx:75` |
| 第一批 | 素材页始终 selectable，管理按钮只在非 selectable 时显示 | 让选择与管理操作并存，恢复“移出素材库”和“在文件夹中显示”。依据 `AssetsPage.tsx:87,168` |
| 第二批 | 首页先放大量统计卡片，需处理项在下方 | 首屏突出需登录账号、失败任务、待发布事项；数据卡支持折叠和自选 |
| 第二批 | 发布时在文案页和官方上传页反复切换 | 在官方页面旁保留发布侧栏，集中素材、文案复制、草稿和发布后核对 |
| 第二批 | 素材/发布记录读取失败被处理为空列表 | 区分加载中、空结果和失败，保留旧数据并提供重试。依据 `AssetsPage.tsx:40`、`PublishPage.tsx:105` |
| 第二批 | 所有账号页禁用后台节流，受保护页面可超过常驻上限 | 分级保留扫码/编辑页面和普通后台页，测量切换延迟、CPU、内存后设置资源预算。依据 `view-pool.ts:512,705` |
| 第三批 | 素材全量渲染、多个视频读取 metadata | 分页或虚拟列表、视区加载、缩略图缓存；用大素材库验证滚动与首屏 |
| 第三批 | CMD 与直接 EXE 默认数据目录不同 | 设置页明确展示当前版本、数据目录，统一启动入口，避免打开另一套登录环境 |

以上性能项是代码风险评估，本次未对实际 CPU、内存或帧率进行基准测试。

## 验证与边界

- CookieGuard、登录检测与身份响应解析的现有测试：3 个文件、159 项通过。
- 额外合成复现证明主页 hydration 期间的负面状态误判。
- 额外真实服务组合复现证明保活任务会阻止自身主页复核；现有调度器测试使用 checkStatus 替身，未覆盖这一组合。
- 真实安装版只读取证，不清理 Cookie、不重置账号、不触发重新登录。
- 尚未进行一次新的真实登录—立即重启—隔夜重启对照，也未验证普通浏览器对照。因此视频号服务端失效的具体触发原因仍需此项证据。
- Electron 的 `expirationDate` 控制本地 Cookie 保留，`flushStore()` 负责把尚未写盘的数据落盘；二者不等于平台确认续期。[Electron 官方 Cookie 文档](https://www.electronjs.org/docs/latest/api/cookies)

建议实施顺序：先修快手保活任务协调、负面结论复核与网页登录上下文；同时补视频号重启诊断；然后处理草稿恢复、状态显示、导航和素材操作，最后依据测量结果改善后台资源与视觉布局。
