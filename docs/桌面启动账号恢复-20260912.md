# 桌面启动账号为空的恢复记录

## 原因与修复范围

安装版 1.0.2 从桌面运行时显示 0 个账号，而先前由 Codex 工具启动的进程能看到 15 个国内账号。现场检查确认两种启动环境访问同一逻辑 Roaming 路径时，实际数据库不同：正常桌面数据库为空，Codex 的 MSIX LocalCache 覆盖文件中保留了完整账号数据库。浏览器配置大部分仍在正常 Roaming 目录内，不能只复制 LocalCache 目录来替代完整资料。

先前在 Codex 工具进程内进行的安装后校验，只验证了该进程所见的数据；它不足以证明正常桌面程序读到了同一数据库。关闭 Codex 连带关闭由工具启动的工作台，是另一个启动生命周期问题。本次修改维护与启动工具，安装程序本身仍为已发布的 1.0.2。

## 恢复方法

1. 正常退出工作台及使用其配置的浏览器。
2. 经现有 Windows Explorer 启动独立维护进程，分别备份真实 Roaming 的完整资料和 Codex LocalCache 的覆盖文件，逐文件校验 SHA-256。
3. 在独立进程中建立临时恢复目录：先复制正常目录的资料，再应用隔离目录的覆盖文件。校验合并后的全部文件、数据库完整性和记录内容。
4. 保留原正常目录，通过同一 Roaming 父目录下的重命名切换到恢复后的目录。隔离目录原件及两个独立备份均保留。
5. 从 Explorer 独立启动现有安装版，以正在运行的程序所读数据库、IPC 返回结果和真实界面共同验收。

合并恢复了 25,189 个文件。恢复时数据为：国内账号 15、国外账号 2、作品 46、数据快照 3,522，国内浏览器分区目录 30、国外浏览器配置目录 2。数据库六类业务记录内容与恢复来源一致，SQLite 完整性检查通过。首次桌面运行后 UI 显示 15 个国内账号，主进程 IPC 与数据库计数相同，后台采集继续新增记录。

正常退出后再次独立启动，UI 仍显示 15 个国内账号、14 个在线；运行中主进程 IPC 返回 15 条，数据库保留 2 个国外账号、46 条作品，快照增加至 3,529，完整性检查通过。一个视频号在恢复后的本次运行中由平台网页重新确认登录身份，未要求重新扫码。其余账号的缓存在线标记不等同于逐个重新登录验收；原先未登录的一个 B 站账号仍保持原状态。

第二次启动记录的实际来源为 Explorer → 独立 helper → 工作台，helper 创建应用前后都不属于 Job。启动 helper 和调用终端退出后，工作台主进程仍存活。工作台因自身 libuv 子进程管理加入 Job 是正常情况，不能把“属于任意 Job”视为“属于 Codex Job”。本次未在工作进行中关闭 Codex 本身；独立性验证依据是上述进程来源及启动者退出后的存活结果。诊断端口已关闭，软件继续运行。

最终通过新的独立维护入口对比升级前完整备份：15 个国内账号、2 个国外账号、46 条作品及原有 3,515 条快照全部保留，快照已继续增长至 3,536；30 个国内分区目录和 2 个国外配置目录全部保留。目录与数据库文件句柄解析的物理路径均为正常 Roaming，当前数据库及备份数据库完整性检查均通过。

## 后续操作约定

- 正常使用桌面快捷方式启动工作台。自动维护后需要启动安装版时，使用 `scripts/start-installed-workbench.ps1`，不要从工具终端直接派生正式程序。
- 备份与验证使用 `scripts/run-installed-maintenance.ps1`，由独立启动器的 `Script` 模式执行。
- 默认 Roaming 的维护入口检查调用进程环境，并通过文件句柄核对目录及数据库实际路径，防止在隔离视图中误报验证通过。
- 进程是否带有任意 Windows Job、包身份 API 返回值、路径字符串是否相同，都不能单独证明软件独立运行或读取了正确数据。需要结合 Explorer 启动来源、实际文件路径和运行中的界面结果。
- 用户数据、恢复脚本和详细本机校验报告保留在本地，不纳入源代码或安装包。

独立启动方法及无害生命周期验证见 [安装版独立启动](independent-installed-launch.md)。
