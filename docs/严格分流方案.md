# 严格分流方案 · 国内走国内网络 + 国际平台接入

> **两句话**
> **国内六平台**:任何带凭据请求,只要不能证明走的是中国大陆直连出口,就不发出 —— 休眠代替,不改道、不回落、不"强制在线"。能不能打开、外网能不能登录,**永不构成放行依据**。
> **国际三平台**:只走官方 API + 强制代理出口,代理不可用就休眠,**禁止回落直连**。
>
> 两组是**镜像约束**:国内组"必须直连、绝不经代理",国外组"必须经代理、绝不直连"。
> 同一个门闩机制,两个相反的方向。
>
> 全部结论来自对本机网络的**实测**与对现有代码的**逐文件核对**。复现脚本在 `scripts/probe-*.mjs`。
> 本版取代上一版:修正了闸门位置(架构级)、补上了最高危入口(全新扫码登录)、更新了环境基线、
> 重写了国际平台接入(旧版那部分是在旧架构下写的,与请求级闸门对不上)。

### 0.1 当前环境(2026-09-06 21:20 实测,**与上一版不同**)

| 项 | 上一版记录 | **现在实测** |
|---|---|---|

`node scripts/probe-chains.mjs` 当前输出:

`213.218.254.3`。`global` 模式下没有"国内通路"这回事,连百度都从日本出境。

这正是异地登录。**这不是假设,是当前状态。**

### 0.3 四个直觉信号在此环境下全部失效

| 信号 | 实测 | 结论 |
|---|---|---|
| DNS 解析 | `dns.resolve4` 全部 `ECONNREFUSED` | ❌ 拿不到(被劫持) |
| TCP 连通 | 全部 0–2ms,对端 `198.18.2.x` | ❌ 恒为真(fake-ip 本地应答) |
| TLS 握手 | 全部成功,证书真实可信 | ❌ 恒为真(Clash 转发真实 TLS,不解密) |
| 绑定物理网卡 | `rule` 与 `global` 下**都 timeout** | ❌ 不可用(`auto-route` 在路由层捕获) |

第 4 条今天在 `global` 下再次复测:绑 `192.168.1.20` 依旧 6015ms timeout。
两种模式都失败,证明这是 `auto-route` 导致,与模式无关 ——
**"绑物理网卡强制直连"这条路在本机不存在。**

### 0.4 关键发现:双枪探测无法产生信号

原计划核心方法是"同一主机打两枪(直连 / 强制代理),比出口"。实测两次:

| 环境 | 默认路由出口 | 经 `127.0.0.1:10090` 出口 | 相同? |
|---|---|---|---|
| `rule` 模式 | 青岛联通 / 东京(按目标分) | 完全相同 | **相同** |
| `global` 模式(今天) | 东京 `213.218.254.3` | 东京 `213.218.254.3` | **相同** |

原因:**mihomo 按目标域名选路,与请求从哪个端口进来无关。**
把请求塞进代理端口,规则照样重新判定一遍。"强制走代理"这个动作**不存在**。

> **结论:双枪必须废弃。** 可用信号只剩两个,必须组合:
> - **Clash `/connections` 的逐 host `chains`** —— 唯一的逐 host 事实来源
> - **打国内回显站的出口归属** —— 必须是中国大陆

## 第 1 部分:三条红线

### 红线 A:国内账号凭据永不经境外出口

- 带 cookie 的一切(采集、登录探针、保活、上传、页面加载)在无法证明走国内出口时**拒绝发出**
- 拒绝形式是**休眠 + 排队**,不是改道重试
- **"代理能打开"、"外网能登录"可以显示,但永不构成放行依据**
- 不提供任何"我知道风险,强制继续"的开关

### 红线 B:不新增高频、指向创作者中心的请求

现状基线(已核对代码):

| 机制 | 频率 | 位置 |
|---|---|---|
| 登录探针最小间隔 | 30 秒 | `account-service.ts:41` |
| 巡检 | 5 分钟 | `account-service.ts:42` |
| 巡检内错峰 | 700ms | `account-service.ts:43` |
| 采集 | 6 小时 + 15% 抖动 | `types.ts:250` / `scheduler.ts:124` |
| 保活 | 12 小时 | `types.ts:251` |

这台机器上有 6 个已登录账号共享一个 IP。抖音的 IP 级验证码会波及全部。
项目立场是"看起来像普通 Chrome"(`user-agent.ts` 整个模块的目的)。

**做法**:网络探测**不打平台域名**。读本地 Clash API(零外网)+ 打中立回显站。
平台可达性**复用现有登录探针**,不新增请求。

### 红线 C:凭据不进 `AppSettings`

实测 `backup.ts:32` 的 `FORBIDDEN_KEYS` 正则:

```
拦截  cookie / cookies / password / passwd / token / access_token /
      refresh_token / secret / sessionid / bduss / sessdata
放行  clashSecret / clashToken / clashApiKey / proxyPassword   ← 驼峰命名绕过
```

正则是 `^(...)$` 全词匹配,所以任何驼峰复合词都会被**明文写进备份**。
且 `settings` 表是单个 JSON blob(`settings.ts` 的 `SETTINGS_KEY = "app"`),
`AppSettings` 全量进 `BackupPayload.settings`。

- Clash 密钥、代理密码一律**不进 `AppSettings`**
- 独立表 + `safeStorage.encryptString()`
- `buildBackup()` 显式排除 + 断言测试

## 第 2 部分:闸门放在哪里(**对上一版的架构级修正**)

上一版写的是"在 `AccountService` 加私有方法 `assertCnEgressOrThrow()`,6 个入口前置调用"。
**这个设计不成立**,有三个理由,逐条核对过代码。

### 2.1 为什么按调用点加闸门堵不住

**理由一:一半的入口不经过 `AccountService`。**

`ipc/handlers/views.ts` 里这些 IPC **直接调 `ViewPool`**,`AccountService` 完全不在调用链上:

| IPC | 实际调用 | 位置 |
|---|---|---|
| `viewReload` | `pool.reload(id)` → `webContents.reload()` | `views.ts:31` |
| `viewBack` | `pool.back(id)` → `navigationHistory.goBack()` | `views.ts:32` |
| `viewForward` | `pool.forward(id)` | `views.ts:33` |

`reload` 会把当前创作者中心页面**整页重新加载**,带全量 cookie。
`AccountService` 上的私有方法拦不到它 —— 它根本不在那条路上。

**理由二:更根本 —— 闸门管的是"导航",泄漏发生在"请求"。**

`showView()` 只在页面**首次**加载时导航一次。之后:

- 视图是**长生命周期**的(`view-pool.ts:42` 注释明确:切换账号只切可见性,视图不销毁)
- `backgroundThrottling: false`(`view-pool.ts:207`),注释说明**隐藏视图也要保持定时器运行**
- 创作者中心都是 SPA,自己在页面里持续发 XHR:轮询消息、刷新数据、心跳

**所以:6 个账号的 6 个 Chromium 视图,即使一次导航都不发生,也在持续自发地带 cookie 发请求。**
把 `showView()` 堵死,已经加载的页面照样在漏。这是上一版最大的漏洞 ——
它防的是"新开页面",而实际风险是"已开的 6 个页面一直在发请求"。

**理由三:漏一个就等于没做。** 6 个入口靠人工枚举维护,以后加任何功能都可能忘。
`git log` 里加载路径这块反复改过多轮,这种约定必然会腐化。

### 2.2 正确的位置:`session.webRequest.onBeforeRequest`

**每个账号的 partition 都有独立 session**(`account-session.ts:49`,
`partitionForAccount(accountId)`)。在这个 session 上装一个请求级闸门:

```ts
// account-session.ts,configured 守卫之外
ses.webRequest.onBeforeRequest((details, callback) => {
  // 非国内平台账号直接放行
  if (groupOf(platformId) !== "cn") return callback({ cancel: false });
  const verdict = gate.verdictFor(platformId);
  if (verdict.allowed) return callback({ cancel: false });
  audit.blocked(accountId, details.url, verdict.reason);
  callback({ cancel: true });          // 请求根本没发出
});
```

**这一个钩子覆盖:**

| 泄漏路径 | 上一版(按调用点) | 本版(webRequest) |
|---|---|---|
| `showView()` 首次导航 | ✅ | ✅ |
| `patrol()` 页内探针 | ✅ | ✅ |
| `go()` 打开上传页 | ✅ | ✅ |
| 地址栏导航 | ✅ | ✅ |
| `ensureView()` 预热 | ✅ | ✅ |
| `scheduler.execute()` 采集 | ✅ | ✅ |
| **`viewReload` 整页重载** | ❌ 漏 | ✅ |
| **`viewBack` / `viewForward`** | ❌ 漏 | ✅ |
| **已加载 SPA 的自发 XHR** | ❌ 漏(最大的洞) | ✅ |
| **页面所有子资源** | ❌ 漏 | ✅ |
| **`collectors` 的 `executeJavaScript` 注入 fetch** | 间接 | ✅ 直接 |
| **未来新增的任何入口** | ❌ 默认漏 | ✅ 默认堵 |

**关键差别是默认方向:** 按调用点加闸门是**默认放行,记得加才堵**;
请求级闸门是**默认堵,只有验证通过才放行**。严格模式只能选后者。

已确认 `webRequest` 在本项目**完全未被使用**(全仓 grep 零命中),
不存在"每个 session 只能有一个监听器"的冲突。

### 2.3 仍然需要的三处调用点检查(纵深防御)

请求级闸门是唯一的**强制**保证,但它在"请求已经产生"这一层拦截。
以下三处额外加前置检查,目的不是安全冗余,而是**体验**和**审计清晰度**:

| 位置 | 目的 |
|---|---|
| `showView()` | 不通过则**不创建视图、不导航**,渲染层直接显示休眠卡片。避免"白屏 + 一堆 cancel 审计" |
| `scheduler.execute()` | 复用现有 `skipped(account, trigger, "等待国内网络出口")`,采集记录里有明确原因,不是 failed |
| `patrol()` | 传 `skipProbe: true`。`login-detector.ts:84` 已有该分支(`if (input.skipProbe) return inconclusive`),只读 cookie 不触网 |

`patrol()` 这一处有个恰好合适的既有逻辑:`detectLoginState` 对曾经 online 的账号
在无法确认时**保持上次结论**(`login-detector.ts:167-186` 一带)。
所以休眠期不会把账号误标成掉线。

### 2.4 一处必须在阶段 2 实测确认的细节

`login-detector.ts:222` 的主进程探针用的是 **`session.fetch()`**
(带 `credentials: "include"`),不是页面内 fetch。6 个平台里有 4 个走这条路
(`probeFromMain: true`:抖音、B站、百家号、视频号)。

**必须实测确认 `session.fetch()` 是否经过该 session 的 `webRequest` 钩子。**
验证方法:装上钩子后对该 session 调一次 `fetch`,看钩子是否触发、`cancel: true` 是否生效。

- 若经过 → 自动被覆盖,无需额外处理
- 若**不经过** → 在 `checkStatus()` 内、调 `detectLoginState` 之前显式加闸门检查,
  国内组未验证时强制 `skipProbe: true`

这条不能靠推测。**阶段 2 的验收项之一就是给出这个实测结论。**

## 第 3 部分:最高危入口 —— 全新扫码登录(上一版完全没提)

### 3.1 为什么它比其他入口都严重

上一版列的 6 个入口都是**已有登录态**的账号复用 cookie。
但还有一条:**账号从零开始扫码登录**(`AddAccountModal.tsx` → `create()` → `showView()` → 扫码)。

这条在境外出口下的后果最重:

| | 复用已有登录态 | **全新扫码登录** |
|---|---|---|
| 平台看到的 | 老账号换了个 IP | **这个账号的登录地就是日本** |
| 风控画像 | 异地登录告警 | **注册地/常用地被写成日本** |
| 可逆性 | 换回国内 IP 后逐渐恢复 | **首次绑定的地理位置长期留在风控档案里** |
| 波及 | 单次会话 | 该账号后续所有登录都被拿来和"日本"比对 |

**"外网能扫码成功"恰恰是最危险的情况** —— 它会成功,然后把这个账号永久标记。
这正是你要的"即使外网可以登录也不能登录"。

### 3.2 处理

登录页也是平台域名的页面,所以**请求级闸门天然覆盖它** —— 这是选 `webRequest`
方案的又一个收益(上一版按调用点的设计需要再手工加第 7 个入口)。

额外做两件事:

1. **`AddAccountModal` 前置拦截**:国内出口未验证时,"添加账号"按钮禁用,
   文案写明"需要中国大陆直连出口才能登录国内平台,当前出口:日本 东京"。
   不让用户走到扫码那一步再失败。
2. **登录成功后记录出口**:`accounts` 表加一列 `firstLoginEgress`(国家/ASN)。
   登录完成瞬间写入当时验证通过的出口。后续若发现某账号的首登出口不是大陆,
   在卡片上长期显示提示 —— 因为这个风险不会自己消失。

## 第 4 部分:探测设计

### 4.1 三个信号源

**信号 1 — Clash API(本地,零外网成本,主信号)**

```
GET /configs      → mode / tun.enable / tun.device / mixed-port
GET /connections  → 逐 host 的 chains        ← 唯一的逐 host 事实来源
GET /proxies      → 当前选中节点(仅用于展示)
```

- 频率 15 秒。纯本地 HTTP,不产生外网流量,零风控风险
- 判定:国内平台域名的 `chains` 首项为 `DIRECT` → 该平台走了直连
- 读不到时(未开 / 换内核 / 端口变 / 加了鉴权)→ **判为不可验证 → 国内组休眠**

**信号 2 — 国内回显站出口归属**

```
国内回显站(myip.ipip.net)→ 必须是中国大陆 IP + 大陆 ASN
```

- 频率 60 秒;休眠期 120 秒
- 无 cookie、无 Authorization、独立 Node HTTP 栈,与业务会话零共享
- **这是国内组放行的必要条件**
- 今天实测该站返回东京 → 直接否决,无需看别的

**信号 3 — 本机路由与网卡(零成本)**

- 是否存在跃点更低的 TUN 默认路由
- 识别 `198.18.0.0/16`(fake-ip)、`Meta` / `utun*` / `wg*` / `Wintun`
- 频率 30 秒。用途是给**可操作的**修复提示,不参与放行判定

### 4.2 判定规则

```
国内平台放行 ⟺ 全部满足:
  (a) Clash API 可读                                  [信号 1]
  (b) mode ≠ global
  (c) 该平台代表 host 的 chains 首项为 DIRECT           [信号 1]
  (d) 国内回显站出口为中国大陆                          [信号 2]

任一不满足 → 该平台休眠。不改道,不 fallback,无强制开关。
```

**按今天环境求值**:(a) 可读 ✓ (b) `global` ✗ → **国内组全部休眠**。
(c)(d) 也都不满足(0/6 DIRECT、出口东京),三重否决一致。

上一版环境(`rule` + 6/6 DIRECT + 青岛联通)→ 四条全满足 → 全部放行。
**两种环境都得到正确结果。**

### 4.3 `/connections` 只有活动连接 —— 缓存是必需的,不是优化

今天的实测把这件事从"细节"变成了"核心问题":**6 个国内 host 里 5 个显示"本次未捕获"**。
`/connections` 只包含**当前活动**连接,短连接在读取前就关闭了。

所以缓存层必须做,规则如下:

| 情况 | 判定 |
|---|---|
| 缓存内有记录,5 分钟内,且为 `DIRECT` | 视为已验证 → 放行 |
| 缓存内有记录,且**非** `DIRECT` | 休眠(**脏记录优先于放行**) |
| 无记录 / 已过期 | **待验证 → 休眠**(保守),并触发一次确认 |

"待验证"的确认方式:由监控层对该平台的**公开域名**(不是创作者中心 API)
发一次匿名轻请求,随后立即读 `/connections` 拿 chain。
每平台每 5 分钟最多一次 —— 远低于现有巡检的 5 分钟带凭据探针。

**默认方向再强调一次:拿不到证据 = 休眠,不是放行。**

## 第 5 部分:架构

```
渲染层(React)      只发指令、显示状态;不碰网络、不碰凭据
      │ IPC(现有 register.ts 的 sender 双校验不变)
      ▼
NetworkMonitor        产出 NetworkSnapshot,逐平台放行结论
      ├─ ClashReader      /configs /connections /proxies + chain 短期缓存
      ├─ EgressProbe      国内回显站(Node HTTP,匿名,独立栈)
      └─ RouteInspector   路由表 + 网卡识别(仅用于修复提示)
      │
      ▼
EgressGate            单一事实来源:verdictFor(platformId) → { allowed, reason }
      │
      ├─ 国内组(cn)  必须直连,绝不经代理
      │   ├─【强制层】session.webRequest.onBeforeRequest  每个账号 partition 一个
      │   │    未验证 → cancel: true + 审计。覆盖导航/XHR/子资源/重载/前进后退
      │   └─【体验层】三处前置检查(showView / scheduler / patrol)
      │        不是安全冗余,是为了不白屏、审计干净、不刷无意义日志
      │
      └─ 国际组(global)  必须经代理,绝不直连          ← 第 13 部分
          ├─【强制层】ProxyTransport 发出前三重断言
          │    host 白名单 + agent 是代理 agent + verdict 合格
          ├─ TokenStore        safeStorage 加密(阶段 1 已建)
          └─ YouTube / X / TikTok API 客户端(主进程 Node,不碰 Chromium)
```

国内组的强制层在 **Chromium session** 上(因为请求由渲染进程发出,只能事后拦);
国际组的强制层在 **Node 传输层**(因为请求由主进程发出,可以事前绑路)。
两组机制不同,但门闩来源是同一个 `EgressGate`。

### 5.1 不变式

```
group === "cn" 的账号 partition,其出网请求要么走已验证的国内直连,要么不存在。
永远没有第三种情况。
```

违反即写安全审计并拒绝。未登记的 host 默认拒绝。

## 第 6 部分:休眠与唤醒

### 6.1 休眠时停什么

- 采集、刷新、登录探针、**保活**(保活也是业务请求)
- 页面加载与页内 XHR(由 `webRequest` 闸门自动实现)
- 未发任务进 `waiting-network` 队列,不丢

### 6.2 休眠时什么照常

这是"不卡壳"的保证:

- 历史数据、指标图表、素材库、发布记录、草稿编辑 —— 全部本地数据,照常
- 账号列表与状态展示(显示上次已知状态,不误标掉线)
- 设置、备份、导出

### 6.3 休眠原因文案(必须具体,不写"网络异常")

| 条件 | 文案 |
|---|---|
| Clash API 读不到 | 无法验证出口路径(代理内核未运行或未开启外部控制),已休眠 |
| `mode === "global"` | Clash 处于全局模式,流量经境外出境,已休眠 |
| chain 非 DIRECT | 该平台流量经 {节点名} 出境,严格模式禁止,已休眠 |
| 国内回显出口非大陆 | 直连出口不在中国大陆({国家} {城市}),已休眠 |
| chain 未捕获且缓存过期 | 出口路径待验证,已休眠 |

按当前环境,用户会看到的是第二条 + 第四条:
「Clash 处于全局模式,流量经境外出境,已休眠」「直连出口不在中国大陆(日本 东京)」。

### 6.4 唤醒

- 连续 **2 次**判定合格(约 30 秒间隔)才唤醒,避免抖动导致反复启停
- 唤醒后先发一次公开轻请求确认 chain,再冲带凭据的队列
- 原顺序发送,可单条取消
- 同一原因只保留一条稳定状态,不刷弹窗

### 6.5 修复引导(不自动改用户配置)

给出三样东西:

1. 当前状态:哪个平台走了哪个节点、出口在哪
2. 需要改什么:切到 `rule` 模式 / 给这些域名加 `DIRECT` 规则
3. **可复制的规则文本**:国内六平台 `topLevelHosts` + 局域网 + `GeoIP,CN → DIRECT`

`platforms.ts` 里已有完整的 `topLevelHosts`(抖音 12 个域、快手 8 个、B站 8 个、
百家号 7 个、小红书 5 个、视频号若干),直接生成规则文本即可,不用手写。

## 第 8 部分:为什么这套方案不会引起风控

| 行为 | 风控等级 | 本方案 |
|---|---|---|
| 国内登录态经境外出口 | **极高**(异地登录) | ✅ 请求级拦截,休眠替代 |
| **全新账号在境外 IP 首次扫码** | **极高**(污染风控档案) | ✅ 拦截 + 禁用添加入口 |
| 同一登录态在两国间跳 | **极高** | ✅ 国内组永不经代理 |
| 高频探平台域名 | 中(IP 级验证码,波及同 IP 全部账号) | ✅ 探测不打平台域名;待验证平台每 5 分钟最多一次公开请求 |
| 已登录私有接口当 ping | 中高 | ✅ 不新增,复用现有探针 |
| 休眠期给国内号保活 | **高** | ✅ 休眠即停保活 |
| 探测与业务共用 cookie 罐 | **高** | ✅ 探测走独立 Node 栈,零 cookie |
| 指纹伪装 / 代理池 / 自动互动 | — | ✅ 继续不做 |

**净效果是风险下降**,而且可量化:当前状态下点开账号 = 从东京登录;
方案落地后 = 不发出任何请求。新增的探测(本地 API + 匿名回显站)
比现有的 5 分钟带凭据巡检**更温和、更不可识别**。

### 8.1 一个诚实的剩余风险:TOCTOU

验证 chain 与实际发出请求之间有时间窗,用户可能在这期间切了节点。
这个窗口**无法靠多检查几次消除**,只能缩小 + 事后校验:

- `webRequest` 闸门在**每个请求**发出前读最新 verdict —— 窗口已缩到 15 秒内(监控周期)
- 采集完成后**再读一次** `/connections`,确认该 host 的 chain 仍为 `DIRECT`
- 若发现实际走了境外 → 写安全审计、标记该账号需复查登录态、通知用户
- 可选:订阅 Clash `/connections` 的 WebSocket,把发现延迟从 15 秒压到 1–2 秒

### 8.2 两个方案之外的建议(与代码无关)

1. **给 Clash 外部控制加 secret**。实测 `127.0.0.1:9790` 无鉴权,
   直接 GET 就能读到你访问过的全部主机列表,而且该 API **可写**(能改 mode)。
   任何本机进程都能读写。这不是本方案引入的,但方案会依赖它。
2. **保持 `rule` 模式**。当前是 `global`,国内平台此刻全部不可用。
   切回 `rule` 后用 `node scripts/probe-chains.mjs` 确认 6 个平台回到 `DIRECT`。

另外 `safeStorage` 在 Windows 上用 DPAPI,绑定的是 Windows 用户账户**不是密码** ——
它防"备份被拷走"和"数据库被直接读取",**不防本机沦陷**。

| 闸门 = `AccountService` 私有方法 + 6 处调用点 | **`session.webRequest.onBeforeRequest` 请求级闸门** | `viewReload`/`back`/`forward` 不经 `AccountService`;已加载 SPA 的自发 XHR 完全不受导航闸门约束(2.1 节) |

| `/connections` 缓存是实现细节 | **缓存是必需组件** | 实测 6 个 host 里 5 个"未捕获"(4.3 节) |
| 国外三平台接入写在旧架构下 | **按新架构重写为第 13 部分** | 旧版假定"调用点闸门",与请求级闸门对不上;且旧版没算类型拆分成本(13.4 节) |
| 封面图三选一 | 定为**必做**,列为阶段 4 | 休眠期"该 partition 零出网"验收项要求 |
| 双枪探测 | 废弃 | 两种模式下两枪出口必然相同,无信号(0.4 节) |
| 绑物理网卡 | 废弃 | `rule` 与 `global` 下均 timeout,`auto-route` 所致(0.3 节) |
| 整组休眠 | 逐平台休眠 | `chains` 是逐 host 的 |

**保留不变的**(核心立场,全部采纳):
国内只走直连、绝不 fallback、休眠 + 排队、匿名探测、探测与业务栈隔离、
国内 cookie 永不经代理、不允许"强制在线"、`RouteDecision` 审计、
探测不打平台域名、显示实际 chain 而非推测。

## 第 13 部分:国际平台接入(YouTube / X / TikTok)

> 本部分按**新架构**重写。旧版这一节是在"`AccountService` 调用点闸门"的假设下写的,
> 与第 2 部分的请求级闸门对不上,不能直接复用。

### 13.1 国际组为什么能做到比国内组更严格

| | 国内组 | 国际组 |
|---|---|---|
| 凭据形态 | Chromium cookie(在渲染进程里) | **OAuth Bearer token**(在主进程内存/加密表) |
| 请求发出方 | 账号的 Chromium 视图 | **主进程 Node `https.request`** |
| 能否绑定出站路径 | ❌ 不能(`auto-route` 捕获,绑网卡实测 timeout) | ✅ **能**(自定义 `agent`) |
| 执法手段 | 检测 + 休眠(事后拦截) | **绑路 + 断言(事前强制)** |

关键差别:国际组**完全不碰 Chromium**,所以不受 fake-ip / auto-route 的限制。
Node `https.request` 支持自定义 `agent`,可以真正强制所有流量走 CONNECT 隧道。
已实测该隧道可用 —— `scripts/probe-egress-dual.mjs` 第 2 段就是零依赖的 CONNECT 参考实现。

**所以国际组不需要"休眠等出口"这种被动手段,它可以直接拒绝在错误路径上发出请求。**

### 13.2 镜像约束

```
国内组:group === "cn"     → transport 只能是 session-direct 或 none,永不是 api-proxy
国际组:group === "global" → transport 只能是 api-proxy 或 none,永不是 session-direct
未登记 host → 默认拒绝
```

两条都违反即写安全审计并拒绝。这是第 5.1 节不变式的完整形式。

### 13.3 `mixed-port` 的限制(必须正视)

0.4 节已证明:**`mixed-port` 在任何模式下都按规则重新选路**。
所以"把请求塞进 `127.0.0.1:10090`"**不等于**"一定走代理节点"。

国际组的保障因此不能只靠"走了代理端口",要三条一起:

1. 目标域名在 Clash 规则里本就走节点(上一版实测 3/3 命中,今天 `global` 模式下也全部走 JP-2)
2. **国际回显站出口不在中国大陆**(若在大陆,三家 API 通常本就不可用,视为代理不合格)
3. 该 host 的 `chains` 首项**不是** `DIRECT`

三条都过才放行。与国内组的四条判定完全对称。

### 13.4 类型拆分(**这是接入的主要工作量,不是 API 调用**)

现有 `PlatformDefinition` 是**围绕浏览器登录**设计的,字段全是创作者中心语义:

```ts
routes: { home, site, login, upload, analytics, works, comments }   // 都是 URL
login: { topLevelHosts, loginPaths, verificationHosts, sessionCookies,
         cookieDomains, pinnedCookies, sessionTtlHours, probe, probeFromMain,
         loginUsesPopup }
```

YouTube 走 OAuth,**这些字段一个都不适用** —— 没有要导航的创作者中心 URL,
没有 session cookie,没有验证码 host,没有登录页路径。硬塞进同一个 interface
会得到一堆 `null` 和"这个字段对国际平台无意义"的注释。

已核对的受影响点:

| 位置 | 问题 | 处理 |
|---|---|---|
| `platforms.ts:9` `PlatformId` 联合类型 | 加 3 个 id | 拆成 `CnPlatformId \| GlobalPlatformId` |
| `platforms.ts:395` `Record<PlatformId, PlatformDefinition>` | 穷尽 Record,加 id 即编译失败 | 拆成两张表 |
| `login-detector.ts:41` `Record<PlatformId, RegExp[]>` | 同上。且国际平台**没有** cookie 登录检测 | 收窄为 `Record<CnPlatformId, RegExp[]>` |
| `ipc.ts:27` `platformIdSchema` | 放宽后,视图类 IPC 会接受 youtube | **必须收窄**,见下 |
| `getPlatform()` 20 处调用 | 大部分假定创作者中心语义 | 收窄为 `getCnPlatform()`,国际组走新函数 |
| `collectors/index.ts` registry | `Map<PlatformId, Collector>` | 收窄为 `CnPlatformId` |
| `read-model.ts:114`、`preview-api.ts:259` | `PLATFORM_IDS.map()` 汇总 | 改为遍历全部两组,分别汇总 |

设计:

```ts
export type CnPlatformId = "douyin" | "kuaishou" | "xiaohongshu"
                         | "bilibili" | "baijiahao" | "weixin_channels";
export type GlobalPlatformId = "youtube" | "x" | "tiktok";
export type PlatformId = CnPlatformId | GlobalPlatformId;

/** 共有的展示层字段 —— UI 只需要这些 */
interface PlatformBase {
  id: PlatformId;
  name: string; shortName: string; color: string; glyph: string;
  group: PlatformGroup;
}

/** 现有的 6 个,结构完全不变 */
export interface CnPlatformDefinition extends PlatformBase {
  group: "cn";
  routes: PlatformRoutes;
  login: PlatformLoginProfile;
  loginMethods: readonly ("qr" | "sms" | "password")[];
}

/** 新增的 3 个 */
export interface GlobalPlatformDefinition extends PlatformBase {
  group: "global";
  api: {
    /** 必须全部在此白名单内,否则传输层拒绝 */
    hosts: readonly string[];
    oauth: { authUrl: string; tokenUrl: string; scopes: readonly string[]; usePkce: boolean };
    /** 用于 chain 校验的代表 host */
    chainHost: string;
  };
  capabilities: {
    readMetrics: boolean;
    listWorks: boolean;
    upload: "direct" | "draft" | false;
  };
}
```

**IPC 收窄是安全项,不是洁癖。** `ipc.ts:27` 的 `platformIdSchema` 若直接放宽到 9 个 id,
`viewShow` / `viewGo` / `viewNavigate` 就会接受 `youtube` —— 而国际平台没有视图可导航。
必须拆成 `cnPlatformIdSchema`(视图类 IPC 用)和 `platformIdSchema`(展示类 IPC 用)。

### 13.5 传输层

```
国际 API 请求 → ProxyTransport
  ├─ 断言 1:目标 host 在该平台 api.hosts 白名单内
  ├─ 断言 2:agent 确实是 CONNECT 代理 agent(不是默认 agent)
  ├─ 断言 3:该平台 verdict.allowed(三条校验都过)
  └─ HTTP CONNECT 隧道(零依赖,node:http + node:https)
```

硬约束:

- 代理不可用 → 国际组休眠,**禁止回落直连**(与国内组禁止回落代理对称)
- OAuth token **只经 ProxyTransport 发出**,任何其他路径拿不到 token
- 只实现 **HTTP CONNECT**。当前 `mixed-port: 10090` 同时支持 HTTP 与 SOCKS5,
  但 SOCKS5 要自己实现握手或加依赖。项目现有**只有 7 个运行时依赖**
  (`lucide-react` / `react` / `react-dom` / `react-is` / `recharts` / `zod` / `zustand`),
  保持这个克制 —— 不为 SOCKS5 加包

### 13.6 OAuth 授权流

```
用户点"授权 YouTube"
  → 主进程起临时 loopback HTTP server(127.0.0.1 随机端口)
  → shell.openExternal() 打开系统浏览器(不是 Electron 窗口)
  → 用户在系统浏览器里登录 Google 并授权
  → 回调打到 loopback,拿 code
  → 用 code 换 token,走 ProxyTransport
  → token 存 credentials 表(safeStorage 加密,阶段 1 已建)
  → 关掉 loopback server
```

三个要点:

- **必须用系统浏览器 + loopback**,不用 Electron 窗口。Google 明确禁止在嵌入式 webview 里做 OAuth,
  而且用系统浏览器就复用了用户已有的登录态,体验更好
- PKCE:X 的 v2 OAuth2 要求;YouTube / TikTok 也支持,一律开
- token 刷新也走 ProxyTransport,刷新失败不回落直连

### 13.7 三家的接入条件

**⚠️ 以下是架构假设。API 定价与准入政策变动频繁,开工前必须重新核对官方文档,不要以本文为准。**
我没有联网核实当期政策,这一节的作用是划定架构边界,不是给出可直接实施的参数。

**YouTube — Data API v3**
- 上传:`videos.insert`,支持 resumable upload(断点续传,适合大文件)
- 数据:`channels.list`(订阅/总播放/视频数)、`playlistItems` + `videos.list`(作品级)
- 深度数据:YouTube Analytics API 是**另一套 scope**,要单独申请
- 认证:OAuth2。上传 scope 属**敏感范围,需应用审核**
- 待核对:当期每日配额、`videos.insert` 单次配额开销、审核周期与材料

**X — API v2**
- 发布:含媒体上传的发帖端点
- 数据:用户与推文指标(字段随访问层级变化)
- 认证:OAuth2 PKCE
- ⚠️ **费用是主要门槛**:免费层写入额度极低、读取几乎不可用。
  **必须先确认当期定价,再决定是否纳入** —— 有可能结论是"不划算,不接"

**TikTok — Content Posting API**
- 两种模式:**Direct Post**(直接发布)/ **Upload to Drafts**(存草稿,用户在 App 内确认)
- 数据:Display API 提供账号与视频基础指标
- 认证:OAuth2
- ⚠️ **准入是主要门槛**:需应用审核;审核前通常只能发草稿且限测试账号。
  可能需企业资质与域名验证

**落地顺序:TikTok → YouTube → X**
- TikTok 第一:**草稿模式最贴合本项目既有哲学** ——
  现有发布流程本来就是"助手打开上传页、最终由人确认",草稿模式语义完全一致
- YouTube 第二:文档最成熟、配额可预测、resumable upload 成熟
- X 最后:**先评估定价再决定接不接**,不排除结论是放弃

### 13.8 国际组的休眠与队列

- 代理连续失败 → 国际组休眠,不改直连
- **两组队列完全隔离,互不阻塞**:国内休眠时国际组照常工作,反之亦然
- 配额接近上限主动降频;上传失败按官方建议退避,不自建激进重试
- 上传中途断路:国内组中止不续传;国际组按官方 resumable 机制恢复

### 13.9 国际组不引入新的风控面

| 行为 | 说明 |
|---|---|
| 用官方 API 而非模拟浏览器 | ✅ 这本身就是**降低**风险 —— 不违反 ToS |
| OAuth 在系统浏览器完成 | ✅ 不在 Electron 里拦 token,不碰用户 Google 密码 |
| 遵守官方速率限制 | ✅ 配额接近上限主动降频 |
| 不做指纹伪装 / 代理池 / 自动互动 | ✅ 继续不做 |
| token 不进备份、不回传渲染层 | ✅ 见第 9 部分 |
