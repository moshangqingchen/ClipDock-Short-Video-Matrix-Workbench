# ClipDock 严格分流方案

> 以现有 Electron 工作台为底座，不另起项目、不另做助手 exe。
> 全部代码断言来自对本仓库的**逐文件核对**，网络断言来自 `scripts/probe-*.mjs` 的**实测**。
> 本版以「主进程三件套」结构为主干，合并了三处事实修正（见第 17 部分）。

---

## 0. 一句话

国内六个平台的账号分区，**只有能证明大陆直连时才出网**；证明不了就休眠排队 ——
即使海外代理能打开 B 站 / 抖音，也不许发带 Cookie 的请求。

国际平台走主进程官方 API + 强制代理，**不进国内 Chromium 分区**。
网络执法全部放在 Electron 主进程。

## 1. 目标与非目标

### 1.1 要交付的

- 国内账号在 mihomo 全局 / TUN 下：**零条**带 Cookie 的境外业务请求
- 代理能打开国内站时，界面仍显示休眠，原因写明「严格模式忽略代理可达」
- 规则模式且大陆直连可验证时：国内采集、保活、发布助手照常
- 顶栏四态：双通路 / 仅国内 / 仅海外 / 全断
- 国内任务进「等待国内网络」，恢复后**连续两次合格**再跑，禁止改代理重试

### 1.2 明确不做

- 不承诺绕过 mihomo TUN 去绑物理网卡（实测超时，见 2.3）
- 不用双枪探测当放行依据（只作诊断，见 5.4）
- 不把 YouTube / X / TikTok 塞进现有 `WebContentsView`
- 不自动点平台发布按钮、不打码、不指纹伪装、不代理池
- **不提供「强制国内上线」按钮**
- 不承诺绝对零风控；本方案只消除「登录态走错出口」这条已知路径

### 1.3 严格模式四条法

```
1. 国内业务只允许已证明的大陆直连。
2. 证明失败 → 休眠，禁止 fallback 代理。
3. 禁止「代理能打开就试试」。
4. 国际业务只允许 ProxyTransport；代理不合格则国际休眠，禁止回落直连。
```

### 2.3 网络实测基线（`scripts/probe-*.mjs`，随时可重跑）

| 项 | 实测值 |
|---|---|
| 代理内核 | mihomo (Clash.Meta)，GUI 为 FlClash |
| TUN | 启用，设备 `Meta`，栈 gVisor，`auto-route: true` |
| 混合端口 | `10090`（HTTP + SOCKS5） |
| 外部控制 | `127.0.0.1:9790`，**无鉴权** |
| 国内出口 | 中国 山东 青岛 联通 |
| 国际出口 | 日本 东京 |

四个信号在此环境下**失效**，方案不能依赖它们：

| 信号 | 实测 | 结论 |
|---|---|---|
| DNS 解析 | `dns.resolve4` 全部 `ECONNREFUSED` | ❌ 拿不到（被劫持） |
| TCP 连通 | 全部 0–2ms，对端 `198.18.2.x` | ❌ 恒为真（fake-ip 本地应答） |
| TLS 握手 | 全部成功，证书真实可信 | ❌ 恒为真（Clash 不解密，转发真实 TLS） |
| 绑定物理网卡 | `global` 与 `rule` 下**都** timeout | ❌ 不可用（`auto-route` 在路由层捕获） |

绑网卡在两种模式下均失败，证明这是 `auto-route` 所致，**与 Clash 模式无关**。
这就是 1.2「不承诺绕过 TUN」的实测依据。

**双枪探测在 rule 模式下无信号**：把请求送进 `127.0.0.1:10090`，mihomo 仍按目标域名选路 ——
国内目标照样 `DIRECT`，国外目标照样走节点，两枪结果必然相同。
所以双枪只能当诊断对照，不能当放行依据（5.4）。

## 3. 架构

```
渲染层（React）
  平台卡 / 四态顶栏 / 队列 / 日志 / 设置
  永不接触 Cookie、Token、Clash secret、代理密码

预加载桥（现有沙箱 IPC，register.ts 的 sender 双校验不变）
  只传账号 id、模式、脱敏出口、决策摘要

主进程（唯一执法点）
  ├── EgressGate         唯一 RouteDecision 来源
  ├── NetworkObserver    Clash/Meta、出口、ASN、DNS、IPv6（诊断）
  ├── DirectProof        国内放行证明（可验证才为真）
  ├── SessionGuard       每个国内 partition 的 webRequest      ← 门 1
  ├── SchedulerGate      采集/保活/探测/打开上传 与门闩成对      ← 门 2
  ├── GatedSessionFetch  包住 login-detector 的主进程探测       ← 门 3
  ├── ProxyTransport     仅国际 API（阶段 4）
  ├── CredentialVault    safeStorage / DPAPI，进不了备份
  └── Audit              无 Cookie、无 Token、URL 只 host+path
```

**不单独做 Windows 网络助手进程。** 国内流量在 Chromium session 里，
外挂 exe 插不进 `webRequest`；TUN 已经把整机吸走，外挂 bind 网卡一样超时（2.3 实测）。
再加一条本地 RPC 只会放大攻击面和崩溃域。

### 3.1 为什么是三道门而不是一道

三道门覆盖三类**不同的**出网路径，缺一不可：

| 门 | 拦什么 | 不装会怎样 |
|---|---|---|
| SessionGuard | 渲染进程发出的一切：导航、重载、前进后退、子资源、XHR、页内 `pageFetch` | 页面照常出网 |
| SchedulerGate | 调度器主动发起的动作：定时采集、保活、状态检查、打开上传页 | 休眠时仍导航/探测，账号被误判为 `network_error`，弹掉线通知 |
| GatedSessionFetch | 主进程 `session.fetch` 探测（**4/6 平台走这条**） | 见 6.2 —— 纵深防御，非唯一依赖 |

单装 SessionGuard 的后果最隐蔽：请求确实被 cancel 了，但调度器不知道，
于是把 cancel 当成"业务失败"，把账号打成 `network_error` 并触发掉线通知。
**状态语义被污染 —— 这不是体验问题，是正确性问题。**

## 4. 平台类型

### 4.1 拆分

```ts
// src/shared/platforms.ts
export type CnPlatformId =
  | "douyin" | "kuaishou" | "xiaohongshu"
  | "bilibili" | "baijiahao" | "weixin_channels";
export type GlobalPlatformId = "youtube" | "tiktok" | "x";

```

现有 `PLATFORM_IDS` 改名 `CN_PLATFORM_IDS`，行为不变。

国内平台继续：官方页登录、独立分区、页内采集、发布助手。
国际平台（阶段 4）：OAuth PKCE、主进程 Token、官方 API，**不进 `AccountWorkspace`**。

### 4.2 真漏洞在 `accountCreate`，不在 `viewShow`

已核对 `ipc/handlers/views.ts:9`：`viewShow` 吃的是 `accountIdSchema`（账号 UUID），
**不收平台 id**。所以 `viewShow("youtube")` 测不到任何东西。

真正的漏洞路径：

```
accountCreate({ platformId: "youtube" })   ← ipc.ts:39 用的是 platformIdSchema
  → 建出一个带 Chromium 分区的国际账号
  → 对该 UUID 调 viewShow(accountId)
  → YouTube 进了国内浏览栈
```

所以阶段 1 必须在 schema 层掐死：

| 位置 | 改法 |
|---|---|
| `ipc.ts:39` `accountCreateSchema.platformId` | 收窄为 `cnPlatformIdSchema` |
| `ipc.ts:27` `platformIdSchema` | 拆两个：`cnPlatformIdSchema`（视图/账号类）、`platformIdSchema`（展示类） |
| `views.ts` 全部 `view*` | 取出账号后**断言** `account.platformId ∈ CnPlatformId`，否则拒绝 |
| 国际账号 | 阶段 4 另开 `GlobalAccount` 表 + 另一组 IPC，**无 partition 字段** |

两层都要：schema 拦住新建，断言拦住存量数据（数据库里可能已有脏数据）。

### 4.3 穷尽 Record 会编译失败（改造时必然撞上）

已核对，两处 `Record<PlatformId, ...>` 加 id 即报错：

| 位置 | 内容 | 处理 |
|---|---|---|
| `platforms.ts:395` | `Record<PlatformId, PlatformDefinition>` | 拆成 `CN_PLATFORMS` / `GLOBAL_PLATFORMS` 两张表 |
| `login-detector.ts:41` | `Record<PlatformId, RegExp[]>` 登出正文特征 | 收窄为 `Record<CnPlatformId, RegExp[]>`（国际平台无 cookie 登录检测） |

另外 `collectors/index.ts` 的 `Map<PlatformId, Collector>` 收窄为 `CnPlatformId`；
`read-model.ts:114`、`preview-api.ts:259` 的 `PLATFORM_IDS.map()` 改为分组汇总。

**这些是编译器会逐个指出的机械改动，不是设计难题。** 但工作量真实存在，
不要低估为"加三个字符串"。

## 5. 网络判定：诊断 ≠ 放行

### 5.1 四态（观察结果，不能单独让国内上线）

| 模式 | 含义 |
|---|---|
| 双通路 | 大陆直连可证明，且国际代理健康 |
| 仅国内 | 大陆直连可证明，代理不健康 |
| 仅海外 | 直连不可证明，代理可用（**含「代理能打开 B 站」**） |
| 全断 | 两路都不可用 |

### 5.2 国内放行证明 DirectProof（必须同时满足）

```
1. 代表国内 host 的链路不是代理链
     Clash /connections 的 chains 首项为 DIRECT，或等价可信证据
2. 直连出口 IP 的 ASN 在中国大陆
3. 国内平台公开轻请求（匿名、无 Cookie）TLS/SNI 正常
4. 未检测到：
     - 直连出口 == 代理出口 且在海外   （全局劫持）
     - 国内域名解析到境外 IP           （疑似污染）
     - IPv6 境外泄漏且无法钉死 IPv4
5. Clash 读不到、TUN 全局、或任何一条存疑
     → DirectProof = false → 国内休眠
```

**默认：不可验证 = 不准出网。**
Clash API 没开、密钥错、mihomo 全局，全部按休眠处理 —— 不要猜「可能还能直连」。

### 5.3 逐平台判定，不是整组

`chains` 是**逐 host** 的，可能出现"抖音走 DIRECT 但小红书被规则误送代理"。
整组休眠会过度，逐平台判定更准。

`/connections` 只含**活动连接**，某平台此刻没连接时 `chains` 查不到。处理：

- 维护短期缓存（5 分钟），记录每个 host 最近一次观测到的 chain
- 缓存内为 `DIRECT` → 视为已验证
- 缓存过期且当前无连接 → 标记"待验证"，首次业务请求前先发一次
  **对该平台公开域名**的匿名轻请求，然后立即读 `/connections` 确认

这样每平台最多 5 分钟一次额外公开请求，远低于现有巡检频率（5 分钟一次带凭据探针）。

### 5.4 双枪只作诊断

2.3 已实测：rule 模式下双枪结果必然相同，**无信号**。

所以双枪只写入 `NetworkSnapshot` 的对照灯：
**「代理可访问国内站」永远不能把直连灯变绿，也不能改 DirectProof。**

### 5.5 探测节奏与风控

| 探测 | 频率 | 成本 |
|---|---|---|
| Clash API（`/configs` `/connections` `/proxies`） | 15s | **零外网**，纯本地 HTTP |
| 出口归属（中立回显站） | 60s，休眠 120s | 匿名，独立 Node 栈 |
| 路由表 + 网卡 | 30s | 零成本 |
| 平台公开域名 | **最多 5 分钟一次** | 匿名，仅在 chain 待验证时 |

硬约束：

- 诊断请求**禁止带任何账号 Cookie / token**，用独立 `net.fetch` + 明确 Agent，
  **不复用账号 session**
- 只打公开页或连通端点，**不打创作者中心、用户信息、作品列表**
- 带登录态的探测（现有 `login-detector`）属于**业务**，必须先过 DirectProof，
  不合格则根本不调用

对比现状基线（已核对代码）：登录探针最小间隔 30s（`account-service.ts:41`）、
巡检 5 分钟（`:42`）、采集 6 小时 + 15% 抖动。
**新增诊断比现有行为更温和、更不可识别。**

## 6. 国内执法面（本项目真正的交付）

三道门，缺一不可。

### 6.1 门 1 · SessionGuard（请求级）

挂在 `configureAccountSession()`（`account-session.ts:47`）。
现有 `configured` WeakSet 守卫（`:31`）只配置一次 —— **门闩要装在守卫外面**，
否则改了不生效；`wipeAccountSession()` 后重建也要再装。

```
session.webRequest.onBeforeRequest：

DirectProof == false
  → cancel: true
  → 记 BlockedRequest（host + path，无 query、无 cookie）

DirectProof == true
  → 放行（仍受 navigation-policy 的 host 约束）
```

**必须覆盖**：顶级导航、重载、前进后退、子资源、XHR、页内 `pageFetch`。
这是唯一能覆盖 `view-pool.ts` 里 `reload()` / `back()` / `forward()` 的层
—— 那三个方法从 `views.ts` 直接调 pool，**根本不经过 `AccountService`**，
任何"在 service 里加前置检查"的设计都拦不住它们。

**运行 vs 休眠两套规则**：

| 状态 | 验证码 / passport subframe |
|---|---|
| 运行中 | **继续放行**（现有 `navigation-policy` 行为，`verificationHosts`） |
| 休眠 | **一并取消** —— 休眠时不应停在登录页往外打 |

不要一个 `cancel()` 打天下。

**粒度是「该账号 session 的全部请求」**，不是「业务 API」。
视频号 `topLevelHosts` 很宽（微信域尤其），只拦业务 API 会放走微信 CDN。

### 6.2 门 3 · GatedSessionFetch（主进程探测）

**先说事实修正。** 上一版方案写"抖音 `probeFromMain: true`"，
已逐平台核对 `platforms.ts`，实际是 **4/6 平台**：

| 平台 | `probeFromMain` | 行号 |
|---|---|---|
| 抖音 | **true** | `:147` |
| 快手 | false | `:195` |
| 小红书 | false | `:244` |
| B 站 | **true** | `:294` |
| 百家号 | **true** | `:337` |
| **视频号** | **true** | `:390` |

**视频号也在里面** —— 按风控代价这是最高的一个。
`session.fetch` 路径的暴露面是 **4/6 平台，不是 1/6**。

调用点 `login-detector.ts:222`：

```ts
const response = await input.session.fetch(platform.login.probe.url, {
  credentials: "include",     // ← 带 Cookie
  ...
});
```

**webRequest 能不能拦住它？答案已在 Electron 类型定义里，不需要当阻塞项。**

`node_modules/electron/electron.d.ts:10201`（`net.fetch`）与 `:12977`（`session.fetch`）：

> By default, requests made with `net.fetch` can be made to custom protocols as well as
> `file:`, and **will trigger webRequest handlers if present**. […]
> **webRequest handlers will still be triggered when bypassing custom protocols.**

连 `bypassCustomProtocolHandlers` 都不是逃生门。所以：

- **SessionGuard 拦得住 `session.fetch`** —— 这是文档保证的行为
- 实测仍要做一次（文档与实际可能有偏差），但**降级为验证项，不是阻塞项**，
  不该挡住阶段 3 开工
- `gatedSessionFetch` **照做** —— 纵深防御。DirectProof 为假时**根本不调用**
  `session.fetch`，直接返回「未探测 / 休眠」

**采集不得改用主进程 fetch 来「绕过页面」。** 这条要写进 code review 清单。

### 6.3 门 2 · SchedulerGate（调度级）

只拦包不够。现有调度在休眠时仍会导航首页、保活、采集失败，
再把账号打成 `offline` / `network_error`，并触发掉线通知。

**保活是实测存在的定时出网**（上一版方案完全漏了）：

```
scheduler.ts:129   if (this.settings.keepaliveEnabled) {
scheduler.ts:130     const interval = this.settings.keepaliveIntervalHours * 3600_000;
scheduler.ts:132     if (sinceOnline >= interval) void this.enqueue(account.id, "keepalive");
scheduler.ts:184   const wc = await this.prepareView(account, collector.workingUrl, item.trigger === "keepalive");
```

`keepaliveEnabled` 默认 **true**，间隔 **12 小时**（`types.ts:251-253`），
会强制打开创作者首页。**这是一条带 Cookie 的定时出网，必须停。**

DirectProof == false 时对该国内账号：

| 动作 | 行为 |
|---|---|
| 定时采集 | 跳过，记 `waiting-network` |
| **keepalive** | **停止**（保活也是带 Cookie 出网） |
| `accountCheckStatus` / 登录探测 | 不发带 Cookie 的 probe（走 6.2 的 gated fetch） |
| `publishOpenUpload` / `publishAttachFiles` | IPC **直接拒绝**，文案「等待国内网络」 |
| 视图 `reload` / `go` / `navigate` | 拒绝或 no-op，并 toast |
| 已打开的视图 | 停加载；不在后台继续跑页面请求 |

`publishOpenUpload` 尤其重要：不要打开上传页再被 webRequest 取消 —— 用户会以为卡死。
IPC 通道名已核对：`ipc-channels.ts:43-44`。

### 6.4 新增 `dormant` 状态

现有枚举（`types.ts:15`）**没有休眠态**：

```ts
export type AccountStatus =
  "unknown" | "online" | "offline" | "needs_verification" | "expiring" | "network_error";
```

必须新增 `dormant`，**禁止复用**：

| 状态 | 语义 |
|---|---|
| `offline` | 登录失效，**要重新扫码** |
| `needs_verification` | 平台要求验证码 |
| `network_error` | **直连证明为真**但业务失败 |
| `dormant`（新） | 出口不合格，**等国内网络**，登录态未知 |

混用会让"要重新扫码"和"等国内网"在 UI 上不可区分，掉线通知也会乱弹。
**休眠不弹「账号掉线」。**

现有 `login-detector.ts:171-180` 有一条既有逻辑：曾经 online 的账号在无法确认时
**保持上次结论**。这正好适合休眠期 —— 不会把账号误标为掉线，可直接复用。

### 6.5 封面图：一条闸门管不到的泄漏

`work.coverUrl` 由渲染层 `<img>` 直接加载

- 处理：改为经 `sv-asset://` 由主进程代理并本地缓存。
  **该协议已存在**（`asset-service.ts:10`），复用即可，顺带减少重复外网请求

## 7. 最高危入口：全新扫码登录

其余入口都是**已有登录态**的账号复用 cookie。还有一条更严重：
**账号从零开始扫码登录**（`AddAccountModal.tsx` → `create()` → `showView()` → 扫码）。

### 7.1 为什么它最严重

| | 复用已有登录态 | **全新扫码登录** |
|---|---|---|
| 平台看到的 | 老设备、老 IP 段、突然换到日本 | **全新设备 + 日本 IP 的首次登录** |
| 风控画像 | 异地登录（可申诉） | **境外注册的新设备**，长期跟随该账号 |
| 可否事后消除 | 换回国内 IP 即恢复 | **不可消除** —— 首登记录留在平台侧 |

SessionGuard 在 DirectProof 为假时取消该 partition 全部请求，
所以这条**被顺带拦住了**。够用。

### 7.2 但存量污染需要能被发现

一种情况是拦不住的：账号**已经**在境外出口登录成功过
（严格模式上线之前建的号），cookie 已经绑在东京 IP 上。
之后即使 DirectProof 恢复为真、一切合规，那个账号的服务端会话
本身就带着一条"日本登录"的历史。

**不是拦截能力的差别，是存量污染的可发现性。** 处理：

```sql
-- migration v2，与凭据表同一批
ALTER TABLE accounts ADD COLUMN first_login_egress TEXT;
```

- 账号首次转为 `online` 时，写入当时的出口国家 + ASN（**不写完整 IP**）
- 已存在的账号该列为 `NULL` → UI 显示"首登出口未知"
- 若记录显示首登出口不在大陆 → 卡片上标注
  **「此账号首登出口异常（{国家}），建议重置登录环境重新扫码」**
- 只提示，**不自动重置** —— 重置会清掉登录态，必须用户决定

### 7.3 添加账号入口

`AddAccountModal.tsx`：DirectProof 为假时**禁用添加按钮**，
文案「等待国内网络后再添加账号」。

这比"允许添加但拦住请求"体验更好：用户不会对着一个永远出不来的二维码等。

## 8. 状态机、队列、唤醒

```
DirectProof true  + 代理健康   → 双通路：国内运行，国际可运行
DirectProof true  + 代理失败   → 仅国内：国内运行，国际休眠
DirectProof false + 代理健康   → 仅海外：国内休眠，国际可运行
DirectProof false + 代理失败   → 全断
```

国内任务状态：`queued | waiting-network | running | done | failed`
**`waiting-network` 没有「用代理立即发送」这个选项。**

### 8.1 唤醒

- DirectProof **连续两次**为真才唤醒（约 30 秒间隔），避免闪断导致反复启停
- 顺序：先匿名诊断 → 再恢复调度 → 再冲队列
- 任务保留原顺序，可单条取消
- **幂等键**防重复采集 / 发布记录

### 8.2 中途断路

国内上传（发布助手填文件）中途 DirectProof 变假：**立刻停，禁止代理续传**。

### 8.3 TOCTOU 窗口

验证 chain 与实际发出请求之间存在时间窗，用户可能在这期间切节点或换模式。
这个窗口**没法靠多检查几次消除**，只能事后校验：

- 采集完成后**再读一次** `/connections`，确认该 host 的 chain 仍为 `DIRECT`
- 若发现实际走了境外 → 写**安全审计** + 标记该账号需复查登录态 + 通知用户
- 可选：订阅 Clash `/connections` WebSocket，把发现延迟从 15 秒降到 1–2 秒

### 8.4 队列隔离

国内 / 国际队列完全隔离，互不阻塞（国际未上线时空实现）。

## 9. 凭据与备份

### 9.1 现有正则的驼峰陷阱（实测）

`security/backup.ts:31` 的 `FORBIDDEN_KEYS` 是**全词匹配**：

```
/^(cookie|cookies|password|passwd|token|access_token|refresh_token|secret|sessionid|bduss|sessdata)$/i
```

| 输入 | 结果 |
|---|---|
| `secret` / `token` / `password` | ✅ 拦截（抛错） |
| `clashSecret` / `proxyPassword` / `accessToken` / `clientSecret` / `idToken` | ❌ **放行，明文写入备份** |

且 `settings` 表是单个 JSON blob（`SETTINGS_KEY = "app"`），`AppSettings` 全量进
`BackupPayload.settings`。**任何驼峰命名的凭据都会漏网。**

### 9.2 处理

```sql
-- migration v2（现有只到 v1，见 migrations.ts:9）
CREATE TABLE IF NOT EXISTS credentials (
  id         TEXT PRIMARY KEY,
  kind       TEXT NOT NULL,   -- 'clash' | 'proxy' | 'oauth'
  account_id TEXT,
  ciphertext BLOB NOT NULL,   -- safeStorage.encryptString 输出
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_credentials_account ON credentials(account_id);
```

- Clash API **地址**可明文进 `AppSettings`；**密钥**进凭据表
- 代理密码进凭据表
- 阶段 4 的 OAuth token 只进凭据表
- `safeStorage.isEncryptionAvailable() === false` → **拒绝保存并提示**，不降级明文
- **`FORBIDDEN_KEYS` 正则保留作第二道断言**，但凭据表**整表不进** `BackupPayload`
  —— 不再依赖字段名过滤
- `backup.test.ts` 加断言：备份产物不含 `credentials` 表内容
- IPC 只暴露「是否已配置 / 是否已授权 / 到期时间 / 撤销」，**永不回传明文**
- 渲染层、日志、toast 不得出现 token、cookie、Authorization、带 query 的地址

### 10.2 国内账号卡

```
  链路  ✓ DIRECT              ← 来自 Clash /connections，是事实不是推测
  出口  中国 · 青岛联通
```

休眠时：

```
小红书 · 种草号
  链路  ✗ 日本 JP-1           ← 规则未命中 DIRECT
  状态  休眠 · 该平台流量经日本出境，严格模式禁止
```

- **直连灯**：仅 DirectProof 为真时绿
- **代理对照灯**：灰字「代理可访问」，**永远不能使账号上线**
- 首登出口异常时额外标注（7.2）
- 最近一次直连验证时间

### 10.3 休眠原因固定文案（必须具体，不写"网络异常"）

| 条件 | 文案 |
|---|---|
| Clash 读不到 | Clash/内核不可读，按不可验证处理，已休眠 |
| `mode === global` | Clash 处于全局模式，流量经境外出境，已休眠 |
| chain 非 DIRECT | 该平台流量经 {节点名} 出境，严格模式禁止，已休眠 |
| 国内出口非大陆 | 直连出口不在中国大陆（{国家}），已休眠 |
| 双出口相同且在海外 | 直连与代理出口相同（流量已被 VPN 接管），已休眠 |
| 域名解析到境外 | 国内域名解析到境外 IP（疑似污染），已休眠 |
| 仅代理可达 | 国际代理可打开该站，严格模式禁止使用，已休眠 |
| chain 待验证 | 出口路径待验证，已休眠 |

### 10.4 修复引导

**不自动改用户配置。** 给出：

1. 当前状态说明（哪个平台走了哪个节点）
2. 需要改什么（切 rule 模式 / 给该域名加 DIRECT 规则）
3. **可复制的规则文本**（国内六平台 `topLevelHosts` + 局域网 + GeoIP CN → DIRECT）

### 10.5 设置

- Clash 外部控制地址、密钥（密钥走凭据表）
- 代理主机 / 端口 / 协议（阶段 4 才用于国际；阶段 2–3 仅诊断）
- 探测间隔
- 严格模式说明（**只读，默认开**）
- **无「强制上线」按钮**

### 10.6 休眠不阻塞 UI

严格模式最大的体验风险是"一直休眠、什么都干不了"。对策：

1. 历史数据、素材库、发布记录、草稿编辑**全部照常**
2. 一键可操作的出路（10.4）
3. **逐平台判定** —— 一个平台被误送代理不影响其他五个
4. 队列不丢
5. 国际组独立 —— 国内休眠时国际照常
